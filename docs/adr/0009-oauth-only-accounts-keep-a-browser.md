# OAuth-only accounts keep a browser, as a fallback the protocol asks for

An account whose only identity is an IdP (Linux.do, GitHub) has no password to log in with, and on a site that grants the daily bonus for logging in, an old session is worthless — the bonus needs a *fresh* login. For those accounts `panel/service.py` runs the protocol attempt first and, only if it fails **and** `login_method` is `linuxdo`/`github`, launches a browser (`panel/browser_login.py`) to log in through the IdP; the session it wins is then used over HTTP. The preferred escape — trading a browser-minted session for a real password via `PUT /api/user/self` (`newapi.bootstrap_password`), after which the account never needs a browser again — is kept and offered in the UI, but it cannot be relied on: New API verifies `original_password` on that route, and an OAuth-only account has no password hash to verify, so forks like agentrouter.org answer `原密码错误`. Alternatives rejected: keeping every account in a browser profile and clicking daily (ADR-0007's reason — slow, fragile); asking the owner to reset the password by email (a manual step per account, and the OAuth account may have no verified email).

**Consequences**:
- The IdP login must be performed by a human once per account, in a visible window ("浏览器登录" in the panel). It is kept alive afterwards by the persistent profile at `<CHECKIN_BROWSER_PROFILE_DIR>/<provider>/<account_name>` — one profile per identity, so two accounts never share cookies. When that profile's IdP session eventually expires, the daily headless run detects the IdP's own login page and fails fast with instructions instead of timing out.
- The site's cookies are cleared before each login (`_forget_site`) while the IdP's are kept: this is the "log out, then log back in" those sites require, without a logout button. Cookies alone are not enough — the SPA keeps the login in `localStorage` and its router sends `/login` to `/console` while that is there, hiding the very OAuth button the run needs, so `_forget_spa_login` clears the storage and comes back to `/login`.
- The browser hop also has to bring back the account's user id (`accounts.api_user`), read from the SPA's `localStorage['user']`: forks that validate the `new-api-user` header against the session 401 every authenticated route without it, which makes a fresh session indistinguishable from a dead one. The session and that id are stored and travel together from then on.
- `checked_in` cannot be observed through the browser hop — the login response goes to the browser, not to us — so success is inferred from the balance moving across the login. When the before-balance is unreadable the outcome is `checked_in=None`, reported as 已重新登录 rather than a claim either way.
- One browser launch per day per OAuth-only account. A wrong password never triggers a browser: that is a credential problem, not a login-method problem.
