# The route that exists is not always the one that works

`sotamodel.net` registers **two** check-in routes and answers 401 on both: the generic `/api/user/checkin` and its own `/api/user/sota-agent-checkin`. The generic one is *switched off* (`/api/status` reports `checkin_enabled: false`), so POSTing it collects nothing — and `newapi.probe` took the first match, which was the dead one. Probing harder cannot fix this: existence and enablement are different questions, and unauthenticated probing can only see the first.

So `CHECKIN_CANDIDATES` is now ordered **most specific first**, and first-match picks the working route. A fork that bothered to add its own check-in is describing itself; the generic route it inherited from upstream is the less likely one to be live. Measured: every other site 404s the sota-agent path, so trying it first costs one request and changes nothing for them. Rejected: reading `checkin_enabled` to skip a disabled route — the field is `False` only on sotamodel, `True` on three sites, absent on agentrouter, and unreadable behind a WAF, so acting on it would be acting on a signal three of seven sites do not send. It is recorded on `SiteInfo` and shown in the account form instead, because it explains *why* the generic route is dead.

The same fork answers **GET on that same path** with a status read that performs nothing: `{checked_in_today, reward_credits, quota_awarded_today}`. That is the first receipt in this codebase that needs neither a browser nor a ledger scrape — the site names its own day. `newapi.checkin_status` reads it, and `service._reconcile` gives it precedence over the quota log. `seekai.cc` turned out to answer the same idea nested under `stats` with a `records` calendar (verified live: `$20/day`, 4 consecutive days), so both shapes are parsed and both sites gained a better receipt than they had.

**Consequences**:
- Probing costs one extra request per site, and one more where a check-in route was found (the status GET). On a slow fork (`api.hcnsec.cn`, 27s for a full probe) that is a real if minor cost. 401 is what proves a status route: a 200 is the admin `/api/user/:id` route eating the segment, which says nothing about a check-in.
- `Outcome.awarded` carries the site's own figure for what it granted, and `Outcome.gain` prefers it over the balance delta. It is the only way to price a bonus set by per-weekday configuration the panel cannot read — and it is immune to usage landing mid-run, which makes a delta lie. `current_quota` from the same response likewise beats a second `/api/user/self` that could race with usage.
- An all-None `CheckinStatus` means **cannot say**, never "no": an unrecognised shape falls through to the quota log rather than failing a good run.
- A status route reporting `today: true` cannot say *who* collected it — it carries a date, not a timestamp, unlike the quota log. So a run that cannot otherwise confirm itself reports 今日已签到 rather than claiming the credit, on the same principle as ADR-0012.
- This site needs no browser and no `visit` declaration: its API is plain `nginx` with no WAF and no Turnstile, so the ordinary `endpoint` path handles it. The owner adds it like any other account.
