# A WAF can hide the API; the browser's own state is then the reading

On 2026-08-17 `agentrouter.org` put an Aliyun WAF slider CAPTCHA in front of `GET /api/user/self` — public routes (`/api/status`) still answer JSON, but every authenticated read answers a 200 HTML challenge page, from httpx *and* from a `fetch()` inside the logged-in browser. Since `newapi.whoami` was the only proof of a login, a browser login that had visibly succeeded was never recognised: the poll loop ran to its timeout, the fresh session was never stored, and the account reported 找不到登录入口 the next day (the stale SPA login in `localStorage` also kept `/login` redirecting to `/console`). The decision: the browser's own state is a first-class source. `panel/browser_login._logged_in` accepts either proof — `whoami`, or the SPA's `localStorage['user']`, which we empty before clicking the OAuth button so its reappearance means *this* login worked — and returns that user object, whose `id`, `username`, `quota` and `checked_in` are what an authenticated read would have said. Rejected: solving the CAPTCHA (a slider needs a human, and defeating a site's protection is not the panel's business), and relaying the WAF cookies to httpx (measured: `acw_tc` + `session` + the browser's UA still get the challenge).

**Consequences**:
- Two accounts on one WAF'd site now check in headless with no human, on the SPA signal alone. `whoami` stays the primary proof, so nothing changes for sites that answer their API.
- Without `/api/user/self` we cannot ask *which* `session` cookie is the live one, so the longest wins: a logged-in New API session carries the user payload (668 chars vs 400 for the pre-login OAuth state). Marked `ponytail:` in the code.
- The login response the SPA keeps often has `quota: 0`, which is a missing number and not a zero balance — so a 0 there is discarded, `last_quota` keeps the last real reading (`COALESCE` in `store.record_result`), and the balance column can legitimately be stale while the WAF is up.
- Its `checked_in` is a **state** flag, not a receipt: measured over four logins in one hour, it stayed `true` while the site's ledger recorded exactly one bonus. So the site's own quota log decides instead — `GET /api/log/self?type=4` is authenticated, not behind the WAF, and says 每日签到成功，增加额度 ＄25 with a timestamp. `service._reconcile` reads it after every attempt: an entry from this run is 签到成功, an older one from today is 今日已签到, none today fails a run that claimed success, and one that appeared despite a failed read-back rescues the run so the scheduler stops retrying a bonus that already landed.
- Anything that reads a JSON body must verify it *is* JSON. `newapi.probe` now requires a JSON content-type before believing a check-in route exists, or a WAF that answers 200 to every path would make every site look like an endpoint one.
- `newapi.bootstrap_password` (ADR-0009's escape from the browser) needs `GET /api/user/self`, so it cannot work on a WAF'd site either. Those accounts stay on the browser path.
