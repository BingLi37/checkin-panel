# A check-in the owner declares, for sites that leave no receipt

`anyrouter.top` grants the daily bonus when an authenticated page loads after 08:30, and writes **no entry in the quota log**. Probing cannot see any of that: the whole site sits behind an Aliyun WAF JS challenge, so `newapi.probe` gets a challenge page for `/api/status` and every candidate route, and even a perfect probe could not distinguish "the bonus landed silently" from "nothing happened". So this one mechanism is *declared*, not discovered: accounts carry `mechanism` ('auto' — the default, probe decides; 'visit' — a page load grants it), and `service._attempt` sends a `visit` account straight to `_browser_visit` without a protocol attempt. Rejected: guessing from a balance that moves for many reasons, and treating the empty ledger as failure — which reported perfectly good runs as 失败.

**A page load grants it because the site's own SPA posts it.** This was first written as "no route to POST", which was wrong and cost a day of 假签到 reports. The route is `POST /api/user/sign_in`, called straight out of the router's mount effect — `useEffect(() => { id > 0 && uD() }, [id])`, where `uD` is `await be.post("/api/user/sign_in")` — so it is unreachable from outside (the WAF) but fires on any authenticated page the panel opens. That is precisely what made the bonus unmeasurable: `browser_visit`'s first `/console` load *spent* the bonus, and the `before` balance read a moment later already contained it, so `before == after` on every run forever and every day reported 今日已签到 on no evidence. So the panel now **holds** that automatic POST back with request interception, reads the true pre-bonus balance, and then posts the route deliberately — the balance either side of that one call is a real before/after, and the route's own answer is the closest thing to a receipt this site gives. Posting it is not an extra action: it is the request the page was going to send anyway, and it is idempotent.

**Consequences**:
- A `visit` run reports `success=True`, with `checked_in` earned rather than assumed: `True` when the balance grew across the deliberate POST, `False` (今日已签到) only when the SPA's POST was really held back and ours still granted nothing, and `None` (已重新登录) when the hold failed and an unmoved balance therefore proves nothing. It cannot lie the other way either — a route answering `success: false` is reported as a failure with its message.
- The comparison is on **`quota + used_quota`**, not `quota`. Spending only moves quota into used_quota, so only a grant raises the total; comparing the bare balance called a $25 bonus "no change" on an account that burned $25 of it in the same window. Upstream `checkin.py` computes its reward the same way.
- The owner must fill in 每日开放时间 for these accounts; the form marks it required. Loading the page before the window opens collects nothing, and `scheduler.due` would otherwise burn a browser launch every 30 minutes all night (ADR-0011).
- The browser is the only client for such a site, including for reading the balance and for posting the check-in: `browser_login._site_user` and `_site_check_in` both go **from inside the page**, where the WAF challenge is already solved, with the `new-api-user` header the fork demands. httpx gets a challenge page instead — that is what `登录失败: HTTP 200 (非 JSON 响应)` was.
- The route says almost nothing: measured, it answers `{"message": "", "success": true}` whether or not it granted anything, and the SPA shows no toast at all for an empty message. So `success: true` is not a receipt — only the balance movement is.
- The login form itself needed two site-specific steps: dismissing the announcement modal, and clicking 「使用 邮箱或用户名 登录」 before the username field exists at all.
